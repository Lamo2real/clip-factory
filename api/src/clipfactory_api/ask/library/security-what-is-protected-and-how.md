## What is protected and how

| Asset | Protection |
|---|---|
| HTTP API | Every route except `/v1/health` needs a valid access token (API Gateway JWT authorizer: issuer, audience, expiry). The user id comes from the token's `sub`, never from the request body, so one user can never reach another's data. |
| Live updates (WebSocket API) | `$connect` needs a valid Cognito **access** token, checked by `cf-prod-ws-authorizer`: RS256 signature against the pool's published keys, issuer, `token_use = access`, the app client id and expiry (no leeway). Each connection is tied to the token's `sub`, and the broadcaster sends only that owner's changes, in the public shape (no internal fields). Connections expire after 2 hours. |
| The token in the WebSocket URL | Browsers cannot send headers on a WebSocket, so the token travels in the `$connect` query string over TLS. It is never logged: the stage access log has a fixed field list (request id, connection id, event, route, status, time, errors) with no query and no headers, data tracing is off, execution logging is at `ERROR`, and the Lambdas never log the token or the raw query. The token itself lives 15 minutes. |
| Platform webhooks (REST API) | Public by design (platforms cannot hold the owner's token), so it is kept apart from the app API: only `/hooks/{platform}` and `/oauth/{platform}/callback`, unknown platforms get 404, bodies over 256 KB get 413, each method is throttled to 10 requests a second (burst 20) with a monthly usage-plan ceiling, and the handler only stores the event (14-day TTL) or answers a challenge. Webhook events can write nothing but `HOOK#` items; the OAuth callback is described in [Platform keys and tokens](#platform-keys-and-tokens). Access logs leave out the query string (OAuth `code` and `state`). Webhook signature checks are not built yet: events are stored as `unverified` and nothing acts on them. |
| Platform stats tokens | Read from Secrets Manager (`cf-prod/platforms/*`) by `cf-prod-stats` and the clip flow's `metrics` step; never written to DynamoDB, logs, responses or WebSocket events. The refresh route never accepts a platform id or URL from the browser: it reads the clip's own posts. Internal stats fields (`statsId`, `refreshStartedAt`, `statsDueAt`, budgets) never leave the API. |
| Meta verify token | An SSM SecureString (`aws/ssm` key), generated by Terraform as a write-only value so it is never in the Terraform state; compared in constant time. |
| Durable flows | Each flow has its own role: checkpoint access only to its own executions (`function:<name>:*`), and only the table, bucket paths, models and vector index it uses. Only the agent's role may send job-flow callbacks, and only to `cf-prod-job-flow`. Execution history (inputs, step results) is kept 14 days and holds ids and statuses, no tokens. |
| Learning memory (S3 Vectors) | Private vector bucket, encrypted at rest (SSE-S3). Every query filters on the caller's `userId`; `/similar` also checks the clip belongs to the caller. Vectors hold clip text and numbers, never media or tokens. A clip thrown away loses its vector. |
| Videos, clips, skills | Private S3 bucket, encryption at rest (SSE-S3), Block Public Access on. Browsers get presigned URLs that expire after 1 hour. |
| Skill text | Written by the owner, so treated as untrusted text in two places. **In the app** it is shown with the app's own markdown renderer, never as HTML: raw HTML stays text, only `http`, `https` and `mailto` links work, images are never loaded, and a test fails if anything uses `dangerouslySetInnerHTML`. **In prompts** it sits inside `<owner_skills>` and is followed only as far as the task's own rules and answer format allow; the agent's hard rules (never publish, only clip what is in the source) still win. Skill files are only ever read by key from the owner's own DynamoDB items: `cf-prod-clip-flow` and `cf-prod-learn` get `s3:GetObject` on `skills/*` and no list. Uploads and edits accept only the caller's own `skills/{userId}/{skillId}/…` keys. |
| YouTube cookies | Stored at `private/<userId>/youtube-cookies.txt`. The API can replace or delete them but never returns them; only the agent reads them, for yt-dlp. |
| Web app | Private S3 bucket readable only by CloudFront (Origin Access Control). HTTPS only. |
| Database | DynamoDB encrypted at rest, point-in-time recovery for 35 days. |
| AWS access from CI | GitHub OIDC; the deploy role trusts only `main` of `Lamo2real/clip-factory-legal`. No stored AWS keys. |
| Runtime permissions | One IAM role per Lambda (nine) and one for the agent runtime. `cf-prod-stats` can only read and write the table and read and refresh platform tokens (no Bedrock, no vectors); only `cf-prod-api`, `cf-prod-hooks`, `cf-prod-clip-flow` and `cf-prod-stats` reach `cf-prod/platforms/*` in Secrets Manager, and the last two can write only the token secrets (`cf-prod/platforms/*/token-*`); `cf-prod-money` (§25) has exactly `cf-prod-stats`' secret access and no DeleteItem; `cf-prod-learn` adds Bedrock and the vector index; `cf-prod-api` may call only `bedrock:InvokeModel` on the help model's EU inference profile and its six EU foundation models (statement `HelpModel`); only the EventBridge rule and `cf-prod-api` may invoke `cf-prod-stats`. Each can reach only the table actions, bucket paths, models, vector index and API it needs. The WebSocket authorizer has no AWS permissions beyond its logs. The agent may call `bedrock:InvokeModel` on the watch model's EU profile and its six EU foundation models (statement `InvokeWatchModel`) besides Fable and Titan, and has no Rekognition, Comprehend, MediaConvert, Step Functions or Batch action (tested in `infra/modules/agent/tests`). The agent cannot publish, change IAM or touch infrastructure. `cf-prod-campaigns` (Content Rewards rules and logos) has no Secrets Manager action at all and only `campaigns/*` in the media bucket ([below](#content-rewards-contracts-38)). |
| Model data | Claude Fable 5.1 runs through the global cross-Region profile, so prompts (transcripts, hooks, captions, and since [ADR-40](DECISIONS.md#adr-40-watch-the-whole-video-before-picking) **frames of the whole source video**: the same class of data as the one facecam frame per clip before, but far more of it) may be processed outside the EU, and with the required `aws_review` data-retention mode AWS may keep them up to 30 days for human review (not shared with Anthropic). Titan embeddings run in `eu-north-1`. The second watcher, Amazon Nova 2 Lite, gets small video parts of the source through the **EU** profile only (eu-central-1, eu-north-1, eu-south-1, eu-south-2, eu-west-1, eu-west-3; the agent's IAM statement `InvokeWatchModel` names exactly that profile and those six foundation models, no wildcard). No frame or video part is stored outside the media bucket in Stockholm (`jobs/{jobId}/source/picture/`, expired after 14 days), and no new bucket or Region holds data at rest. Help questions go to Claude Haiku 5.5 through the **EU** profile only (EU Regions), and only after search found a match; they are not stored by Clip Factory. Media and data at rest stay in Stockholm. |
| Ask Clip Factory (help assistant) | Two routes behind the same JWT as every `/v1` route ([CONTRACTS.md §19](CONTRACTS.md#19-ask-clip-factory-grounded-in-app-help-assistant-owner-request-2026-11-16)). It reads **no** clips, posts, weeks or settings for its answers: live numbers are fetched by the browser from the existing routes with the owner's own token. Questions, history, answers and skills are never stored and never logged (one outcome line with a request id per request; the generic access line has no body). The question, history and knowledge go to the model as JSON data fields, and the system prompt says they are data, not instructions; the owner's skills block comes first, as in every model call ([§18.6](CONTRACTS.md#18-skills-full-create-read-update-delete-every-ai-call-uses-every-skill-owner-request-2026-11-16)), and the grounding rules after it say the skills never override facts from the knowledge. Model output is checked: action ids must come from this request's matches, and every bold button name, path and number must appear in the matches; an answer with a link or a domain the matches do not hold, or one that repeats a price the owner typed (a number from the question with a money word or currency sign within 24 characters), is thrown away too, and the plain answer is used (outcome `kb_ungrounded`). The model client makes one attempt only (no retry). History from the browser is never trusted for buttons. Questions about passwords, keys, tokens, the cookie file's contents, other people's accounts or clips, or the servers get a fixed refusal with no model call. |
| Help knowledge (corpus) | Generated from the app's own source at build time; a filter drops ARNs, account numbers, AWS key ids, emails, `s3://` and signed URLs, and words such as password, secret, token, lambda, dynamodb, bedrock, cognito; a test fails if any survive. The API fetches the deployed copy only from `APP_URL`: it reads the `cf-help-corpus` meta tag in `index.html` and accepts only `/assets/help-corpus.<12 hex>.json` on the same origin (no other host is ever fetched; 3 s timeouts, 512 KB and 2 MB size limits), validates it, and otherwise keeps the last good copy or the copy bundled in the Lambda zip. |
| Pictures in Ask | [CONTRACTS.md §26](CONTRACTS.md#26-pictures-in-ask-owner-request-2026-11-19), [ADR-48](DECISIONS.md#adr-48-ask-pictures-go-inline-are-read-once-into-words-and-are-never-stored). Up to 4 pictures per question exist only in the browser's memory (object URLs, revoked on Start over, on sign-out and past 12 kept) and in that one request; nothing is written to DynamoDB, S3 or logs (the log line has only a count and a size). The browser re-encodes each picture through a canvas (the photo's EXIF and GPS are left behind) and drops every APP1..APP15 and COM segment; the API checks each one (strict base64, a JPEG with a baseline or progressive frame, at most 600 KB and 1600 px) and drops APP1..APP15 and COM again before Bedrock. The model reads them through the same EU profile as help questions; text in a picture is data, never instructions, and what it reads (`words`, `seen`) passes the sensitive filter, loses links, email addresses and long digit runs, and can only change which help doc search finds: answers stay grounded as above, and refusals run on the typed question only. Bedrock model-invocation logging stays off (a test fails if `infra/` defines it). 40 picture questions per owner per day and a `pictures` switch attribute bound the cost. |
| Help cost and abuse | Per owner 6 questions a minute and 60 an hour, 2,000 model answers per 30 days, each reserved with one conditional DynamoDB write; over the limit answers `429` with `Retry-After`, which the app never retries by itself. A deploy flag and a kill-switch item turn it off without a deploy, and the switch also stops the app's local fallback. |
| Owner email | A GitHub secret, so it is masked in the logs of this public repository. |
| Social app keys and account tokens | AWS Secrets Manager only, never DynamoDB, logs, responses, URLs or the browser after the owner pastes them ([details](#platform-keys-and-tokens)). |
| Content Rewards | One sign-in through the Mac app's loopback door; the token only in Secrets Manager and used only by `cf-prod-api`, `cf-prod-clip-flow` and `cf-prod-stats`; brand text is untrusted and checked by code; the reader of brand text (`cf-prod-campaigns`) has no secret access ([details](#content-rewards-contracts-38)). |
| Publishing | Only after the owner presses Keep on that clip (and, for TikTok, fills in the Post to TikTok sheet). The agent has no permission to publish or to read platform secrets. |
| Desktop app | Opens only the app's own address; any other link opens in the normal browser. It holds no keys or secrets, and sign-in works exactly as in a browser. Built by GitHub Actions from this repository and served from the private web bucket over HTTPS. |
