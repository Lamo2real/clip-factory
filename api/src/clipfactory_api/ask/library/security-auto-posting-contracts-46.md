## Auto-posting (CONTRACTS §46)

The owner can let the oldest clips in Review go up by themselves every X hours
([CONTRACTS.md §46](CONTRACTS.md#46-auto-posting-the-oldest-clips-in-review-go-up-by-themselves-every-x-hours-owner-request-2026-11-22),
[ADR-81](DECISIONS.md#adr-81-auto-posting-an-hourly-eventbridge-rule-a-due-check-and-uploads-own-code),
[ARCHITECTURE.md flow 23](ARCHITECTURE.md#23-auto-posting-the-hourly-tick-the-due-check-and-uploads-code-contracts-46-adr-81)).
It is off for everyone until he turns it on, so nothing is posted without his Upload unless he chose this.

| What | How it is protected |
|---|---|
| The role `cf-prod-fn-autopost` | Carries the `cf-prod-role-boundary` permissions boundary and holds exactly what the code calls ([CONTRACTS.md §46.11](CONTRACTS.md#4611-lambda-and-terraform-new-module-inframodulesautopost-wired-in-envsprod)). DynamoDB `GetItem`, `PutItem`, `UpdateItem`, `Query`, `BatchGetItem`, `TransactWriteItems` and `ConditionCheckItem` on the table and `index/*`: read the settings and the clips, claim the run, Upload's conditional transaction, record the outcome. Never `DeleteItem` (nothing is deleted except by TTL) or `Scan` (the owners come from one `Query` of the registry). `lambda:InvokeFunction` only on the clip flow (`cf-prod-clip-flow:*`, to start executions on its `live` alias), no other function. No Secrets Manager action at all: the campaign fit check (`contentrewards.fit.for_clip`, §46.5 rule 4) reads only the table, never a key or token (`SECRET_PREFIX` is set only so its Content Rewards helpers exist; their Secrets Manager client is never called). No S3 (a run reads no files and signs no links), no Bedrock, no vectors, no `iam:*`, `events:*` or `scheduler:*`. Logs and X-Ray as the money module. `autopost.tftest.hcl` fails if any of this widens. |
| Why that is least privilege | The function never posts by itself: it confirms clips with Upload's own transaction and starts the clip flow, which does the posting with its own role, as after Upload. So it needs no platform tokens to publish, no secrets, no media and no model; the campaign fit check reads only stored items. It cannot read any platform's keys or the Content Rewards token. |
| Who can start it | Only the EventBridge rule `cf-prod-autopost-hourly` (an `aws_lambda_permission` for `events.amazonaws.com` with the rule's ARN as the source). It has no URL and no API route, and its handler runs the owners' runs only for an EventBridge event (`source == "aws.events"`). |
| The test runs | `POST /v1/autopost/run` (Practice run now, Private test run) is behind the same JWT as every `/v1` route, acts only on the caller's own clips (the user id comes from the token's `sub`), runs inline in `cf-prod-api` with Upload's existing grants (cf-prod-api's function, role and policy are unchanged), and is limited to one a minute (409). |
| Private test posts | Only the private test run sets the internal `postOptions.test = "private"`; no route body can (`post_preset.clip_options` keeps refusing unknown keys). YouTube uploads it private, Facebook keeps it a draft on his Page, Instagram never publishes it, X is left out, and none joins the stats poller. |
| Nothing unwanted, nothing twice | TikTok is never posted by a run (TikTok's rules want the creator's own pick each time). Campaign clips and clips with a failed important check wait for his Upload. Each clip goes through Upload's conditional transaction and the clip flow's fixed execution name, so a retried or overlapping run can confirm and start it only once. **Throw away** stops a clip when its 8-second Undo has passed before the clip's turn (the decline is sent only then); switching off starts no new run. |
| Settings and data | `autoPost` is checked on the server (unknown keys and `onAt` are refused with a 400). Only new sort keys (`AUTOPOST`, `AUTORUN#` with a 180-day TTL, the registry `AUTOPOSTOWNERS`) and attributes; no new table, index, secret, bucket or Cognito change, and the deploy's delete gate still passes. |
| Why not EventBridge Scheduler | A schedule the app rewrites would need `iam:PassRole`, which the `cf-prod-*` boundary forbids. One fixed hourly rule keeps the deploy role and the boundary exactly as they are. |
