## Your bank (CONTRACTS §40.5)

Your bank shows, per place and per money type, the money his own bank booked that came from an app, tagged "Your bank
says" ([CONTRACTS.md §40.5](CONTRACTS.md#405-your-bank-what-really-reached-it-read-through-enable-banking-owners-choice-a-2026-11-22),
[ADR-82](DECISIONS.md#adr-82-your-bank-enable-banking-restricted-mode-read-once-a-day-keep-only-matched-app-money),
[ARCHITECTURE.md flow 25](ARCHITECTURE.md#25-your-bank-the-connect-flow-through-bank-done-and-the-daily-read-contracts-405-adr-82),
the steps in [SETUP_POSTING.md](SETUP_POSTING.md#your-bank)). The owner chose this way (option A, Enable Banking) on
22 Nov 2026. Clip Factory never moves money and never asks for, sees or stores a bank login: BankID happens on
Enable Banking's page and his bank's own page (PayPal's password on PayPal's). It adds two runtime secrets, two Deny
statements and one api setting; no Allow statement, Lambda, table or Terraform-made secret.

| What | How it is protected |
|---|---|
| The switch | Everything sits behind `BANK_READING` (Terraform `bank_reading_enabled`, **default `false`**). While off, `GET /v1/getpaid/bank` answers `{"on": false}`, every other bank route 503 (so no key, app ID or bank link can be made), and every screen keeps "Clip Factory can't see your bank. Look in your bank's app to see what arrived." It is switched on by one PR after the four builders merge, and turning it off again is the same one line: stored deposits, learned payers, links and secrets stay (his records). The switch is an api setting only: `cf-prod-money`'s daily read doesn't read it and reads every `BANKLINK#` that is still `connected`, and `cf-prod-hooks`' callback doesn't read it either, so a connect started just before the switch goes off can still save its link. To stop the reads at once he taps "Stop reading" on each bank **before** the switch goes off (the money found stays) ([If something goes wrong](#if-something-goes-wrong)). |
| Enable Banking's terms (three conditions) | Restricted mode is free and limited to linked accounts "solely for evaluation purposes or for the personal use of private individuals" (Terms of Service, last updated 9 Jan 2026). Clip Factory keeps all three conditions: **his own** Control Panel account and app (he signs up himself; no step uses **Share**, and step 6 says "Don't tap it"); **only his own personal accounts** (every `POST /auth` sends `psu_type: "personal"`, and the callback drops every account Enable Banking marks `usage: "ORGA"` before it is read; no step ever taps **Request**, the button next to "please request activation" or "please request unrestriction", the paid path for companies); **nobody else** (the first signed-in user who makes a bank key is written to `BANKOWNER` with a conditional put, and anyone else gets 403 "Your bank is only for the owner of this Clip Factory."). |
| The terms risk | The same Terms grant no right "to use the API for any commercial purpose whatsoever", the docs call restricted mode "individual non-commercial use", and the Terms forbid access "through the use of bots … or other automated devices or mechanisms"; a breach "shall result in termination of access" and his liability is not capped. Creator income on a personal account, read by a daily job, is a grey area. So the bank page starts with an optional step holding a ready email that asks Enable Banking exactly this (he sends it himself; nothing waits for it), Clip Factory reads as little as it can (below), and if Enable Banking says no or sends notice, "Stop reading" on each bank and then `bank_reading_enabled = false` is the way back ([If something goes wrong](#if-something-goes-wrong)). |
| The two secrets | `cf-prod/platforms/bank/app`: `privateKeyPem` (PKCS#8), `publicKeyPem`, `certificatePem`, `hashKey` (32 random bytes, base64), `appId`, `source`, `keyMadeAt`. `cf-prod/platforms/bank/token_{linkId}`, one per bank link: `sessionId`, `accounts [{uid, idHash}]`, `validUntil`, `bank`, `country`, `connectedAt`, `closeLater` (old session ids still to close, at most 3). Both are made at runtime with tags `app=cf-prod`, `platform=bank`, never in Terraform (so a deploy can't touch them), and never in DynamoDB, logs, responses, URLs, live events, push messages or the browser. A link's `BANKLINK#{linkId}` item in DynamoDB holds only its state (the bank's name and country, how many accounts it shared, when it ends, how its reads went), never its session or an account's uid. |
| Who can reach them | Today's Allow statements already cover both names, so no Allow is added. `…/bank/app`: written by `cf-prod-api` (the key, the .pem), read by `cf-prod-api`, `cf-prod-hooks` (the callback, through its `…/platforms/*/app*` get grant) and `cf-prod-money` (the reads). `…/bank/token_{linkId}`: created or put by `cf-prod-hooks` (the callback, through its `…/platforms/*/token*` grant), put back without `closeLater` and deleted by `cf-prod-api`, read by `cf-prod-money`, `cf-prod-api` (stop, forget, closing) and `cf-prod-hooks` (on a reconnect the callback reads the old secret fresh for its session id, through the same `…/platforms/*/token*` grant). |
| The `token_` name and the Deny | The session secret's name has an **underscore**, `token_{linkId}`, never a dash, so it never matches the `cf-prod/platforms/*/token-*` put grant that `cf-prod-money`, `cf-prod-clip-flow` and `cf-prod-stats` hold for rotated platform tokens: none of them can overwrite a bank session. `cf-prod-clip-flow` and `cf-prod-stats` can still read `cf-prod/platforms/*`, so each role policy gains one in-place statement, `{Sid = "NoBankSecrets", Effect = "Deny", Action = ["secretsmanager:GetSecretValue"], Resource = ["${trimsuffix(var.platform_secrets_arn, "*")}bank/*"]}` (`infra/modules/flows/main.tf`, clip-flow only, and `infra/modules/stats/main.tf`), and an explicit Deny beats their Allow. `terraform test` checks the Deny is on those two roles only. |
| Fresh reads | Every read of `…/bank/app` and `…/bank/token_{linkId}` uses `Secrets.read(name, fresh=True)` (a few reads a day), never the 5-minute cache of `oauth/secrets.py`, so a new key, a reconnect or a Stop is seen at once by every container. A read acts on a link only when the secret's `connectedAt` equals the link's (read again once, else the link is skipped), so a reconnect can never be ended by its old session. |
| The bank key | "Make my bank key" makes an RSA-4096 key pair and a self-signed certificate (CN "Clip Factory", 10 years, SHA-256) in `cf-prod-api` and writes them straight into `…/bank/app`. He copies only the **public** part into Enable Banking's **Generate outside the browser and import public certificate**; the private key and `hashKey` never leave Secrets Manager and the memory of `cf-prod-api`, `cf-prod-hooks` and `cf-prod-money`, and the view carries only the public key and the certificate. A new key (`again`) or a new app ID is refused with 409 "Stop reading every bank first." while any link still has a session, and a new key keeps `hashKey`, so stored ids never change. |
| The .pem exception (kept for his OK) | If he already followed Enable Banking's default, its browser saves the app's **private** key as a `.pem` file in Downloads. Step 5's folded upload or paste box takes that file once, over HTTPS (`PUT /v1/getpaid/bank/app`, at most 8 KB, a PKCS#8 RSA key of 2048 bits or more), straight into the same secret. It is the **one place** the private key passes through his browser and his Downloads folder, against the rule that it never does. So the screen first says "Better: make a new app with **Generate outside the browser and import public certificate**", the paste box has `autoComplete="off"` and `spellCheck={false}` and is emptied after the send and when the page closes, the key is never logged, echoed or stored outside the secret, and the line "Now delete the .pem file from Downloads." stays until he taps "I deleted it". Removing the box is a one-file change in the web if he says no ([ADR-82](DECISIONS.md#adr-82-your-bank-enable-banking-restricted-mode-read-once-a-day-keep-only-matched-app-money)). |
| The signed token | Each call to Enable Banking carries a new RS256 JWT (`kid` = his app ID, `iss` "enablebanking.com", `aud` "api.enablebanking.com", one hour), made for that call or run only: never kept, never logged, and sent only to `https://api.enablebanking.com` (never the old `api.tilisy.com`). |
| Least data, in memory | Of each transaction only `credit_debit_indicator`, `status`, `transaction_amount`, the booking date, `entry_reference`, `debtor.name` and `remittance_information` are looked at; nothing else is read. Only a booked credit (`CRDT` and `BOOK`, checked again) with a sane amount and currency goes on, and only one that names an app in Clip Factory's own word list or matches a Google or Whop payout record is kept. Everything else (his salary, a Swish, a debit, a balance, his name, address, IBAN and account ids from the callback, other people's payments) is dropped when the page is done: never stored, logged, cached or sent. |
| Least data, stored | A matched payment (`DEPOSIT#`, `state "matched"`): the day, the amount in minor units with its exponent, the money type, the place, how it matched, the payout it paired with, the bank link's own id, a keyed id, and for a match by payer or by his answer the payer's keyed hash (so he can undo it). A payment waiting for his answer: the same, with the payer's keyed hash, plus Clip Factory's own word for the app named, kept until he answers and about 180 days at most (`ttl` is the later of the booking day and the read day, plus 180 days; DynamoDB can take days to delete it, so the view hides it once `ttl` has passed). "Not money from an app": only its keyed id, day, link id and why, for 400 days, and the payer's keyed hash joins `BANKPAYERS.notIncome` until Forget my bank, so it isn't asked about again. Payers he confirmed: `BANKPAYERS.rules` maps keyed hashes to places. **Never stored**: a name (not even the payer's), an account number or its last 4, an IBAN, a balance, a debit, another payment, the bank's text, his IP address or browser. |
| Keyed hashes | `depositId` and `payerKey` are HMAC-SHA256 with `hashKey` (in the secret only), never a plain hash: a plain hash of a day and an amount, or of a payer's name, could be guessed back. Neither holds the account's id or hash, so a reconnect gives the same ids. |
| Logs and errors | Logs carry counts only (`bank.read`: link, pages, seen, kept, asked, matched, dropped) and Enable Banking's error code; never an amount, a name, a text, an IBAN, a uid, a session id, a hash, the IP or the user agent. Bank code raises only its own error types, which carry Enable Banking's `error` code and the HTTP status, never the answer's body, so the generic `http.internal` line can't hold bank data either. |
| The PSU headers (his IP, browser and language) | Sent only for **his own** bank Check now: `cf-prod-api` puts his IP (`requestContext.http.sourceIp`), User-Agent (at most 512 characters) and Accept-Language (at most 100) into the async event for `cf-prod-money` (no retry, no failure destination; Lambda drops it after an hour), and the handler drops them when the event is more than 120 s old, because then he has left. They go to Enable Banking only when his bank lists `required_psu_headers` and all of them can be filled (all or none), for that one read. They are **never stored, never logged** and never in a response. Every other read is unattended and sends none. The public callback's access log records the caller's IP address like every callback (30 days), so the privacy page says only that a Check now's IP address is never stored. |
| How often it reads | Once a day in `cf-prod-money`'s 06:00 UTC run, plus his own bank Check now (at most once every 15 minutes and 12 times a day). At most 3 unattended reads in any rolling 24 hours per link (the PSD2 rule allows 4), a 6-hour pause when a bank says it had too many, and a lease on `BANKCONN.readLease` so two reads (or a read and Forget) never meet. Money's own Check now never reads the bank. |
| Connect and the way back | `POST /v1/getpaid/bank/connect` uses §17's signed single-use state (`OAUTH#{nonce}`, `platform: "bank"`); `bank` is accepted only on `/oauth/bank/callback` (`CALLBACK_ONLY`), so `/hooks/bank` is 404. The callback trusts only that state, never a cookie (BankID can bring him back in another browser), and always answers `302 {APP_URL}/bank-done?result={code}` with a code from a fixed list, `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. `/bank-done` is a public page that needs no sign-in, makes no API call and shows no data. The code, the state, the session id, uids, hashes and the query are never logged. |
| What the API answers | No answer ever carries a private key, `hashKey`, a session id, a uid, an `identification_hash`, a `payerKey`, the bank's own text, an IP address, a user agent or a JWT. Only these routes reach outside stored items: the key (no network), the app check (`GET /application`), the bank list (`GET /aspsps`, cached), connect (`POST /auth`), the two deletes and a view with sessions still to close (`DELETE /sessions`), and Check now (the async invoke). |
| Stop and Forget | "Stop reading Swedbank" closes the session at Enable Banking (which closes the bank's link "if possible") and deletes `token_{linkId}`; when that close fails, the secret stays with `closePending` until a later view, Stop or Forget closes it. "Forget my bank" (refused while a read holds the lease) stops every link, deletes every `DEPOSIT#`, `BANKPAYERS` and every `BANKLINK#` whose session is closed (one still closing keeps only its id, bank and status until the close works), and keeps the bank key and app ID so Connect works again. Both are only ever his own tap, with an 8-second Undo. He can remove the app itself on Enable Banking's **API applications** page. |
| What Enable Banking keeps | Its end-user Privacy Notice (7 Mar 2025): account data "a maximum of 60 seconds", session data up to 180 days, IP address and user agent 30 days, in the EEA (Google Cloud in Dublin, AWS in Luxembourg). It is a registered account information service provider supervised by Finland's FIN-FSA. |
| Notifications | "Money reached your bank from YouTube: 1,234.56 SEK." and the question, link-ending and link-ended messages (`notify.getPaid`) never hold a link, a secret, an account number or the bank's text, and none is sent for old money found by a link's first read. |
