# Security

## The owner's stance

The owner asked for convenience over strictness: "I don't care about security at all. Just make sure that I don't
have to log in every single day or every single week." So the app keeps sign-ins rare, has no multi-factor prompt,
and merges and deploys without a human approval step.

Convenience does not mean open. The app holds the owner's videos, unpublished clips, skills, YouTube cookies and
the keys to the owner's social accounts. Everything below stays on because it costs the owner nothing
in daily use.

## Sign-in and tokens

| Setting | Value | What it means for the owner |
|---|---|---|
| Users | One, created by Terraform from `CF_OWNER_EMAIL`; sign-up is off | Nobody else can create an account. |
| Sign-in | The app's own screen, Secure Remote Password (SRP) through Amplify | The password is never sent in clear text, not even over HTTPS. |
| Access and ID tokens | 15 minutes | Refreshed silently in the background; the owner never notices. |
| Refresh token | 30 days, **rotated on every refresh**, 10-second grace period | Every refresh issues a new 30-day refresh token. Using the app at least once a month means never signing in again. After 30 days away, one sign-in. |
| Token revocation | On | Signing out revokes the refresh token. |
| User existence errors | Hidden | A wrong email and a wrong password give the same message. |
| MFA | Off | Owner's choice. Can be turned on later in Cognito without code changes. |

Tokens are stored by Amplify in the browser's local storage on each device. Signing out on one device does not sign
out others until their refresh token is used and found revoked.

## What is protected and how

| Asset | Protection |
|---|---|
| HTTP API | Every route except `/v1/health` needs a valid access token (API Gateway JWT authorizer: issuer, audience, expiry). The user id comes from the token's `sub`, never from the request body, so one user can never reach another's data. |
| Live updates (WebSocket API) | `$connect` needs a valid Cognito **access** token, checked by `cf-prod-ws-authorizer`: RS256 signature against the pool's published keys, issuer, `token_use = access`, the app client id and expiry (no leeway). Each connection is tied to the token's `sub`, and the broadcaster sends only that owner's changes, in the public shape (no internal fields). Connections expire after 2 hours. |
| The token in the WebSocket URL | Browsers cannot send headers on a WebSocket, so the token travels in the `$connect` query string over TLS. It is never logged: the stage access log has a fixed field list (request id, connection id, event, route, status, time, errors) with no query and no headers, data tracing is off, execution logging is at `ERROR`, and the Lambdas never log the token or the raw query. The token itself lives 15 minutes. |
| Platform webhooks (REST API) | Public by design (platforms cannot hold the owner's token), so it is kept apart from the app API: only `/hooks/{platform}` and `/oauth/{platform}/callback`, unknown platforms get 404, bodies over 256 KB get 413, each method is throttled to 10 requests a second (burst 20) with a monthly usage-plan ceiling, and the handler only stores the event (14-day TTL) or answers a challenge. Webhook events can write nothing but `HOOK#` items; the OAuth callback is described in [Platform keys and tokens](#platform-keys-and-tokens). Access logs leave out the query string (OAuth `code` and `state`). Webhook signature checks are not built yet: events are stored as `unverified` and nothing acts on them. |
| Platform stats tokens | Read from Secrets Manager (`cf-prod/platforms/*`) by `cf-prod-stats` and the clip flow's `metrics` step; never written to DynamoDB, logs, responses or WebSocket events. The refresh route never accepts a platform id or URL from the browser: it reads the clip's own posts. Internal stats fields (`statsId`, `refreshStartedAt`, `statsDueAt`, budgets) never leave the API. |
| Meta verify token | An SSM SecureString (`aws/ssm` key), generated by Terraform as a write-only value so it is never in the Terraform state; compared in constant time. |
| Durable flows | Each flow has its own role: checkpoint access only to its own executions (`function:<name>:*`), and only the table, bucket paths, models and vector index it uses. Only the agent's role may send job-flow callbacks, and only to `cf-prod-job-flow`. Execution history (inputs, step results) is kept 14 days and holds ids and statuses, no tokens. |
| Learning memory (S3 Vectors) | Private vector bucket, encrypted at rest (SSE-S3). Every query filters on the caller's `userId`; `/similar` also checks the clip belongs to the caller. Vectors hold clip text and numbers, never media or tokens. A clip thrown away loses its vector. |
| Videos, clips, skills | Private S3 bucket, encryption at rest (SSE-S3), Block Public Access on. Browsers get presigned URLs that expire after 1 hour. |
| Skill text | Written by the owner, so treated as untrusted text in two places. **In the app** it is shown with the app's own markdown renderer, never as HTML: raw HTML stays text, only `http`, `https` and `mailto` links work, images are never loaded, and a test fails if anything uses `dangerouslySetInnerHTML`. **In prompts** it sits inside `<owner_skills>` and is followed only as far as the task's own rules and answer format allow; the agent's hard rules (never publish, only clip what is in the source) still win. Skill files are only ever read by key from the owner's own DynamoDB items: `cf-prod-clip-flow` and `cf-prod-learn` get `s3:GetObject` on `skills/*` and no list. Uploads and edits accept only the caller's own `skills/{userId}/{skillId}/…` keys. |
| YouTube cookies | Stored at `private/<userId>/youtube-cookies.txt`. The API can replace or delete them but never returns them; only the agent reads them, for yt-dlp. |
| Web app | Private S3 bucket readable only by CloudFront (Origin Access Control). HTTPS only. |
| Database | DynamoDB encrypted at rest, point-in-time recovery for 35 days. |
| AWS access from CI | GitHub OIDC; the deploy role trusts only `main` of `Lamo2real/clip-factory-legal`. No stored AWS keys. |
| Runtime permissions | One IAM role per Lambda (nine) and one for the agent runtime. `cf-prod-stats` can only read and write the table and read and refresh platform tokens (no Bedrock, no vectors); only `cf-prod-api`, `cf-prod-hooks`, `cf-prod-clip-flow` and `cf-prod-stats` reach `cf-prod/platforms/*` in Secrets Manager, and the last two can write only the token secrets (`cf-prod/platforms/*/token-*`); `cf-prod-money` (§25) has exactly `cf-prod-stats`' secret access and no DeleteItem; `cf-prod-learn` adds Bedrock and the vector index; `cf-prod-api` may call only `bedrock:InvokeModel` on the help model's EU inference profile and its six EU foundation models (statement `HelpModel`); only the EventBridge rule and `cf-prod-api` may invoke `cf-prod-stats`. Each can reach only the table actions, bucket paths, models, vector index and API it needs. The WebSocket authorizer has no AWS permissions beyond its logs. The agent may call `bedrock:InvokeModel` on the watch model's EU profile and its six EU foundation models (statement `InvokeWatchModel`) besides Fable and Titan, and has no Rekognition, Comprehend, MediaConvert, Step Functions or Batch action (tested in `infra/modules/agent/tests`). The agent cannot publish, change IAM or touch infrastructure. |
| Model data | Claude Fable 5.1 runs through the global cross-Region profile, so prompts (transcripts, hooks, captions, and since [ADR-40](DECISIONS.md#adr-40-watch-the-whole-video-before-picking) **frames of the whole source video**: the same class of data as the one facecam frame per clip before, but far more of it) may be processed outside the EU, and with the required `aws_review` data-retention mode AWS may keep them up to 30 days for human review (not shared with Anthropic). Titan embeddings run in `eu-north-1`. The second watcher, Amazon Nova 2 Lite, gets small video parts of the source through the **EU** profile only (eu-central-1, eu-north-1, eu-south-1, eu-south-2, eu-west-1, eu-west-3; the agent's IAM statement `InvokeWatchModel` names exactly that profile and those six foundation models, no wildcard). No frame or video part is stored outside the media bucket in Stockholm (`jobs/{jobId}/source/picture/`, expired after 14 days), and no new bucket or Region holds data at rest. Help questions go to Claude Haiku 5.5 through the **EU** profile only (EU Regions), and only after search found a match; they are not stored by Clip Factory. Media and data at rest stay in Stockholm. |
| Ask Clip Factory (help assistant) | Two routes behind the same JWT as every `/v1` route ([CONTRACTS.md §19](CONTRACTS.md#19-ask-clip-factory-grounded-in-app-help-assistant-owner-request-2026-11-16)). It reads **no** clips, posts, weeks or settings for its answers: live numbers are fetched by the browser from the existing routes with the owner's own token. Questions, history, answers and skills are never stored and never logged (one outcome line with a request id per request; the generic access line has no body). The question, history and knowledge go to the model as JSON data fields, and the system prompt says they are data, not instructions; the owner's skills block comes first, as in every model call ([§18.6](CONTRACTS.md#18-skills-full-create-read-update-delete-every-ai-call-uses-every-skill-owner-request-2026-11-16)), and the grounding rules after it say the skills never override facts from the knowledge. Model output is checked: action ids must come from this request's matches, and every bold button name, path and number must appear in the matches; an answer with a link or a domain the matches do not hold, or one that repeats a price the owner typed (a number from the question with a money word or currency sign within 24 characters), is thrown away too, and the plain answer is used (outcome `kb_ungrounded`). The model client makes one attempt only (no retry). History from the browser is never trusted for buttons. Questions about passwords, keys, tokens, the cookie file's contents, other people's accounts or clips, or the servers get a fixed refusal with no model call. |
| Help knowledge (corpus) | Generated from the app's own source at build time; a filter drops ARNs, account numbers, AWS key ids, emails, `s3://` and signed URLs, and words such as password, secret, token, lambda, dynamodb, bedrock, cognito; a test fails if any survive. The API fetches the deployed copy only from `APP_URL`: it reads the `cf-help-corpus` meta tag in `index.html` and accepts only `/assets/help-corpus.<12 hex>.json` on the same origin (no other host is ever fetched; 3 s timeouts, 512 KB and 2 MB size limits), validates it, and otherwise keeps the last good copy or the copy bundled in the Lambda zip. |
| Help cost and abuse | Per owner 6 questions a minute and 60 an hour, 2,000 model answers per 30 days, each reserved with one conditional DynamoDB write; over the limit answers `429` with `Retry-After`, which the app never retries by itself. A deploy flag and a kill-switch item turn it off without a deploy, and the switch also stops the app's local fallback. |
| Owner email | A GitHub secret, so it is masked in the logs of this public repository. |
| Social app keys and account tokens | AWS Secrets Manager only, never DynamoDB, logs, responses, URLs or the browser after the owner pastes them ([details](#platform-keys-and-tokens)). |
| Publishing | Only after the owner presses Keep on that clip (and, for TikTok, fills in the Post to TikTok sheet). The agent has no permission to publish or to read platform secrets. |
| Desktop app | Opens only the app's own address; any other link opens in the normal browser. It holds no keys or secrets, and sign-in works exactly as in a browser. Built by GitHub Actions from this repository and served from the private web bucket over HTTPS. |

## Platform keys and tokens

The owner pastes each platform's app keys into the setup ([SETUP_POSTING.md](SETUP_POSTING.md)) and presses Connect
([CONTRACTS.md §17.4–17.6](CONTRACTS.md#174-api-all-jwt-5-errors-routessetuppy-package-clipfactory_apioauth)).

| What | How it is protected |
|---|---|
| App keys (`clientId`, `clientSecret`, `configId`) | Sent once over HTTPS to `PUT /v1/setup/{platform}/keys` (JWT), written to Secrets Manager `cf-prod/platforms/{platform}/app`, never returned. Responses, DynamoDB and live events carry only masked hints (first 6 and last 4 characters of the public id, "••••" and the last 4 of a secret). The paste box is cleared after saving. |
| Account tokens | Written by `cf-prod-hooks` after the code exchange to `cf-prod/platforms/{platform}/token`; refreshed by `cf-prod-clip-flow` and `cf-prod-stats`. Instagram signs in with a Facebook **user** access token (exchanged for the long-lived one), but only the chosen Page's access token is kept here, with the Instagram account id and Page id; the user token is never stored. Posting and numbers use the Page token. Meta's several-account choices wait in `…/pending` for at most 30 minutes. Never in DynamoDB, logs, responses, URLs, WebSocket events or the durable execution history (steps return ids, not tokens). |
| Secret lifecycle | Created at runtime with `CreateSecret` (tags `app=cf-prod`, `platform`), updated with `PutSecretValue`, deleted with `ForceDeleteWithoutRecovery` on Disconnect or key delete. Logs name the secret, never its value. |
| Who may read them | `cf-prod-api` (create, put, get, describe, delete on `cf-prod/platforms/*`), `cf-prod-hooks` (public, so the narrowest: get and describe only on the `app` secrets `cf-prod/platforms/*/app*`; create, put, get, describe on the token secrets `cf-prod/platforms/*/token*`; the same plus delete on the `pending` secrets `cf-prod/platforms/*/pending*`. No `-` before the `*`, because for a secret that does not exist yet Secrets Manager checks the bare name, and the callback needs "not found", not "access denied", to create it), `cf-prod-clip-flow` and `cf-prod-stats` (get on `cf-prod/platforms/*`, but put only on the token secrets `cf-prod/platforms/*/token-*`, the ARN pattern Terraform passes in as `platform_token_secrets_arn`). Only `cf-prod-api` can write or delete the `app` secrets; only `cf-prod-api` and `cf-prod-hooks` can write the `pending` secrets. `cf-prod-hooks` reaches only the `HOOK#`, `OAUTH#` and `USER#` partitions of the table (`dynamodb:LeadingKeys`). The job flow, the agent, the WebSocket Lambdas and `cf-prod-learn` have no Secrets Manager access. |
| Connect state | `state = v1.{nonce}.{exp}.{HMAC-SHA256}` with the key in `cf-prod/oauth/state-key` (generated by Terraform as a write-only value, never in its state), valid 10 minutes, bound to the platform, and consumed once with a conditional delete of `OAUTH#{nonce}`. A tampered, expired, reused or cross-platform state ends as "That took too long". |
| PKCE | S256 for YouTube and X. The verifier is derived from the nonce with the state key, so it is never stored or sent to the browser. TikTok and Meta use the client secret on the server instead. |
| Redirects | Every platform has one exact redirect URI, `{hooks_url}/oauth/{platform}/callback`, compared exactly by the platform. The callback always answers `302` to `{app_url}/settings/posting/setup/{platform}?result={code}` with a code from a fixed list: nothing from the request is reflected, so it cannot be an open redirect. `Cache-Control: no-store`, `Referrer-Policy: no-referrer`. The code, state and query are never logged. |
| Scopes | Only what posting and numbers need (CONTRACTS §17.7). A missing permission is detected and reported; Meta calls send `appsecret_proof`. |
| Disconnect and data | Disconnect revokes the token where the platform allows it, deletes the token secret and marks the account `not_connected`. For YouTube it also removes stored YouTube numbers (`forget`), as YouTube's Developer Policies require after revocation. Facebook keeps only the Page token, which cannot revoke the app, so the owner removes the app in Facebook's Business integrations settings ([After setup](SETUP_POSTING.md#after-setup)). |
| TikTok verification file | `POST /v1/setup/tiktok/verification-file` accepts only `tiktok*.txt` names and at most 4 KB of printable text, and writes only `tiktok*` keys in the web bucket. |
| Public pages | `about.html`, `legal/privacy.html` and `legal/terms.html` are static and hold no data. |

## CORS

The API allows only the app's CloudFront address and `http://localhost:5173` (local development), and exposes one
response header, `retry-after`, so the help panel can show its countdown. Media bucket CORS
allows `PUT` from the same origins for uploads.

## What is deliberately relaxed

- No MFA, long-lived sessions (30 days, rotating).
- Pull requests merge automatically when CI is green, and `main` deploys without approval. CI is the gate.
- The deploy role may use broad permissions (`PowerUserAccess`), because only `main` of this repository can assume
  it. It still cannot make itself an administrator: IAM is limited to `cf-prod-*` roles that carry the
  `cf-prod-role-boundary` permissions boundary ([DEPLOYMENT.md](DEPLOYMENT.md) section 2), and the desktop build job,
  which runs npm and cargo, cannot ask for its OIDC token.
- No AWS WAF in front of CloudFront or the APIs (cost, one user; the JWT and WebSocket authorizers reject everything
  else, and the public REST API is throttled). A WAF web ACL can be attached to the REST API stage later.
- Webhook signatures are not verified yet; stored events trigger nothing.
- The owner's Google app is **published but not verified** ([ADR-33](DECISIONS.md#adr-33-posting-setup-bring-your-own-keys-with-a-guided-list-per-platform)):
  Google shows "Google hasn't verified this app" on Connect, which is expected for an app only its owner uses.
  Instagram's Meta app stays in Development mode. Neither widens who can use the app: only the owner's accounts
  can connect, and only the owner can sign in to Clip Factory.
- The desktop `.dmg` and `.exe` are not code-signed yet ([ADR-19](DECISIONS.md#adr-19-unsigned-desktop-builds-for-now)).
  Download them only from the app's own Get the app card, never from a copy someone sends you.

## If something goes wrong

- **Lost device**: in the Cognito console, open `cf-prod-users` → Users → your user and sign the user out globally
  (`AdminUserGlobalSignOut`), which revokes every refresh token. Then reset the password from the same page.
- **Leaked cookies file**: delete it in Settings (or `DELETE /v1/settings/cookies`) and sign out of YouTube in the
  browser it came from, which invalidates those cookies.
- **Suspicious deploy**: check the Actions run that produced it; revert on `main`.
- **Leaked webhook verify token**: change the parameter's value version in Terraform (`value_wo_version`) and deploy;
  then paste the new value into the platform console.
- **A leaked platform key** (Client secret or App secret): make a new secret on the platform (Google **Add secret**
  then **Disable** the old one; TikTok, Meta and X **Reset** or **Regenerate**), paste it in Settings › Posting › Set up
  posting › {Platform} › **Save keys**, then **Connect again**. To cut a platform off at once, press **Disconnect**
  (it revokes the token where the platform allows it and deletes the token secret) or remove the app's access on the
  platform (for Google: <https://myaccount.google.com/permissions>).
- **The help assistant says something wrong or unwanted**: set the kill switch (`HELP` / `SWITCH`, `enabled: false`, or
  `model: false` to keep answers from search only) with the command in
  [DEPLOYMENT.md](DEPLOYMENT.md#ask-clip-factory-kill-switch); it takes effect within 60 seconds, no deploy needed.
- **A live connection you do not recognise**: sign out globally (above). Existing connections close within 2 hours at
  the latest, and no new one opens without a valid token.
